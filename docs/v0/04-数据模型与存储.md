# 数据模型与存储

## 1. 存储基线

初版使用本机 SQLite 数据库作为唯一主存储，不使用 Markdown、JSON 或 JSONL 文件保存权威任务数据，也不需要独立数据库服务。SQLite 数据库不用于多台机器共享。

默认数据库路径：

- Windows：`%LOCALAPPDATA%\agent-steward\steward.db`；
- macOS：`~/Library/Application Support/agent-steward/steward.db`；
- Linux：`${XDG_DATA_HOME:-~/.local/share}/agent-steward/steward.db`。

用户可以通过全局选项 `--database <path>` 覆盖默认路径。测试必须使用临时数据库，不能读写用户默认数据库。

默认路径首次创建时必须限制为当前用户可访问：Unix 类系统的应用目录使用 `0700`，数据库及其 `-wal`、`-shm` 文件不得放宽于 `0600`；Windows 使用仅授予当前用户和必要系统主体访问权的 DACL。自定义 `--database` 路径如果无法证明权限满足要求，CLI 必须返回稳定警告，不能声称内容已加密。

每个连接至少设置：

```sql
PRAGMA foreign_keys = ON;
PRAGMA journal_mode = WAL;
PRAGMA busy_timeout = 5000;
```

初版由 Rust CLI 使用同步 SQLite Adapter 直接访问数据库。结构化 `--input` 只接受经过 Schema 校验的 UTF-8 JSON；Markdown 可以作为用户明确导入的 Session 内容或未来导出格式，但不能绕过 Application Service 修改数据库。

## 2. Schema

数据库包含以下初版表。所有时间使用 UTC RFC 3339 字符串；所有布尔语义使用 `0/1`；JSON 字段由 Application Service 在写入前校验。

### `schema_migrations`

| 字段 | 类型 | 约束 |
| --- | --- | --- |
| `version` | INTEGER | PRIMARY KEY |
| `description` | TEXT | NOT NULL |
| `applied_at` | TEXT | NOT NULL |

migration 以递增版本内嵌在应用中。应用发现数据库版本高于自身支持版本时必须拒绝写入，不能自动降级。

### `tasks`

| 字段 | 类型 | 约束 |
| --- | --- | --- |
| `id` | TEXT | PRIMARY KEY |
| `title` | TEXT | NOT NULL |
| `status` | TEXT | NOT NULL，CHECK `open/in_progress/blocked/closed` |
| `version` | INTEGER | NOT NULL，初始为 1 |
| `goal` | TEXT | NOT NULL |
| `scope` | TEXT | NOT NULL |
| `acceptance_criteria` | TEXT | NOT NULL |
| `next_step` | TEXT | NULL |
| `block_reason` | TEXT | NULL |
| `block_recovery` | TEXT | NULL |
| `current_session_id` | TEXT | NULL，引用 `sessions.id` |
| `repository_path` | TEXT | NULL |
| `repository_common_dir` | TEXT | NULL，规范化 Git RepositoryIdentity |
| `repository_branch` | TEXT | NULL |
| `worktree_path` | TEXT | NULL |
| `latest_checkpoint_id` | TEXT | NULL，引用 `checkpoints.id` |
| `closure_outcome` | TEXT | NULL，CHECK `completed/partial/cancelled/superseded` |
| `closure_reason` | TEXT | NULL |
| `closed_at` | TEXT | NULL |
| `created_at` | TEXT | NOT NULL |
| `updated_at` | TEXT | NOT NULL |

`current_session_id` 和 `latest_checkpoint_id` 的外键应为 `DEFERRABLE INITIALLY DEFERRED`，使 Task 与子记录可以在同一事务中一致更新。它们必须使用包含 Task ID 的复合外键，保证引用的 Session 或 Checkpoint 属于当前 Task，而不只是“某条记录存在”。`acceptance_criteria` 保存人类可读文本，不要求把每条标准拆成独立表。

状态字段还必须满足以下行级约束，并由 Application Service 重复校验：`version >= 1`，`title/goal/scope/acceptance_criteria` 去除首尾空白后非空；`blocked` 当且仅当 `block_reason` 和 `block_recovery` 都非空；`closed` 当且仅当 `closure_outcome` 和 `closed_at` 非空，且 `partial/cancelled/superseded` 的 `closure_reason` 非空；`closed` 的 `current_session_id`、`next_step` 和阻塞字段必须为空。`repository_path`、`repository_common_dir`、`repository_branch` 和 `worktree_path` 必须全部为 `NULL` 或全部非空，禁止半登记状态。合法转换以 CLI 文档中的状态表为准。

### `sessions`

| 字段 | 类型 | 约束 |
| --- | --- | --- |
| `id` | TEXT | PRIMARY KEY |
| `task_id` | TEXT | NOT NULL，引用 `tasks.id` |
| `source` | TEXT | NULL |
| `external_session_id` | TEXT | NULL |
| `continued_from` | TEXT | NULL，引用 `sessions.id` |
| `record_path` | TEXT | NULL |
| `started_at` | TEXT | NOT NULL |
| `ended_at` | TEXT | NULL |

`record_path` 只是用户明确提供的外部记录引用，不表示文件内容已进入数据库。文件存在时保存规范化绝对路径；文件不存在时保存调用时展开的绝对弱引用并在查询时警告。`external_session_id` 非空时 `source` 也必须为非空字符串，且相同 `source + external_session_id` 保持唯一。表必须额外提供 `UNIQUE(id, task_id)`，供 `continued_from` 和其他子记录使用复合外键；`continued_from + task_id` 必须引用同一 Task 的 Session。一个本地 Session 只属于一个 Task；Application Service 还必须拒绝 self-reference 和继续关系环，并保证 `tasks.current_session_id` 指向的 Session 的 `ended_at` 为 `NULL`。

### `checkpoints`

| 字段 | 类型 | 约束 |
| --- | --- | --- |
| `id` | TEXT | PRIMARY KEY |
| `task_id` | TEXT | NOT NULL，引用 `tasks.id` |
| `session_id` | TEXT | NOT NULL，引用 `sessions.id` |
| `summary` | TEXT | NOT NULL |
| `completed_json` | TEXT | NOT NULL，JSON array |
| `decisions_json` | TEXT | NOT NULL，JSON array |
| `pending_json` | TEXT | NOT NULL，JSON array |
| `next_step` | TEXT | NOT NULL |
| `risks_json` | TEXT | NOT NULL，JSON array |
| `git_head` | TEXT | NULL，仅为创建时观察快照 |
| `created_at` | TEXT | NOT NULL |

Checkpoint 的 `git_head` 用于恢复提示，不是当前 Git 状态的权威来源。表必须提供 `UNIQUE(id, task_id)`；`session_id + task_id` 必须复合引用同一 Task 的 Session，禁止跨 Task Checkpoint。

### `task_notes`

| 字段 | 类型 | 约束 |
| --- | --- | --- |
| `id` | INTEGER | PRIMARY KEY AUTOINCREMENT |
| `task_id` | TEXT | NOT NULL，引用 `tasks.id` |
| `session_id` | TEXT | NULL，引用 `sessions.id` |
| `note_type` | TEXT | NOT NULL，`decision/progress/risk` |
| `text` | TEXT | NOT NULL |
| `created_at` | TEXT | NOT NULL |

`session_id` 非空时必须与 `task_id` 复合引用同一 Task 的 Session。

### `history`

| 字段 | 类型 | 约束 |
| --- | --- | --- |
| `id` | INTEGER | PRIMARY KEY AUTOINCREMENT |
| `task_id` | TEXT | NOT NULL，引用 `tasks.id` |
| `sequence` | INTEGER | NOT NULL |
| `change_type` | TEXT | NOT NULL |
| `session_id` | TEXT | NULL，引用 `sessions.id` |
| `occurred_at` | TEXT | NOT NULL |
| `summary` | TEXT | NOT NULL |
| `payload_json` | TEXT | NULL |

`UNIQUE(task_id, sequence)` 保证单个 Task 的 History 顺序唯一。sequence 必须在同一写事务内分配。

`session_id` 非空时必须与 `task_id` 复合引用同一 Task 的 Session。V0 的 `change_type` 和 `payload_json` 最低合同固定如下；payload 使用 camelCase，不得放入 Session BLOB、Token 或授权头：

| `change_type` | `payload_json` 最低字段 |
| --- | --- |
| `task.created` | `title` |
| `task.claimed` | `sessionId`、`previousSessionId`、`takeOver` |
| `task.updated` | `changedFields`，按字段名字典序 |
| `task.noted` | `noteId`、`noteType` |
| `task.blocked` | `reason`、`recovery` |
| `task.unblocked` | `nextStep` |
| `checkpoint.saved` | `checkpointId`、`sessionId`、`gitHead` |
| `session.attached` | `sessionId`、`source`、`externalSessionId` |
| `session.resumed` | `sessionId`、`continuedFrom`、`displacedSessionId` |
| `session.closed` | `sessionId`、`wasCurrent` |
| `session.imported` | `importId`、`sessionId`、`sha256`、`sizeBytes` |
| `session.import_removed` | `importId`、`sessionId`、`sha256`、`removedAt` |
| `worktree.created` | `repositoryPath`、`repositoryCommonDir`、`worktreePath`、`branch` |
| `worktree.adopted` | `repositoryPath`、`repositoryCommonDir`、`worktreePath`、`branch` |
| `worktree.removed` | `repositoryPath`、`repositoryCommonDir`、`worktreePath`、`branch` |
| `worktree.detached` | `repositoryPath`、`repositoryCommonDir`、`worktreePath`、`branch` |
| `task.closed` | `outcome`、`reason`、`closedSessionId` |

表中允许为 `null` 的字段仍必须显式存在。通过当前 version 返回的同状态 no-op 不写 History；真正 mutation 缺少对应 History 时必须整体回滚。

### `session_imports`

该表仅用于用户明确执行 `session import add` 时保存导入副本，不要求初版自动解析完整聊天。

| 字段 | 类型 | 约束 |
| --- | --- | --- |
| `id` | TEXT | PRIMARY KEY |
| `session_id` | TEXT | NOT NULL，引用 `sessions.id` |
| `source_path` | TEXT | NOT NULL，导入时已存在的规范化绝对路径 |
| `media_type` | TEXT | NULL |
| `sha256` | TEXT | NOT NULL |
| `content` | BLOB | NOT NULL |
| `imported_at` | TEXT | NOT NULL |

`UNIQUE(session_id, sha256)` 防止相同 Session 重复保存同一内容。来源客户端读取 `sessions.source`，不在 Import 表重复保存。DTO 的 `sizeBytes` 使用 BLOB 字节长度派生，不另存冗余字段。

导入内容不参与 Task 状态推断。用户必须在导入前检查敏感信息；普通 `session attach --record-path` 只保存路径，不复制文件。V0 只接受不超过 16 MiB 的普通文件；实现必须在有界流式读取时计算 SHA-256，拒绝目录、设备、Socket、FIFO 和超过上限的输入。`session import remove` 删除该行并通过 History 保留不含原文的最小审计元数据；任何 V0 Query 都不得再返回已删除内容或 Import 元数据。

### 同 Task 复合外键

Migration 必须建立以下关系；左侧引用字段中可空 ID 为 `NULL` 时允许没有目标，否则目标必须属于同一 Task：

| 引用字段 | 目标字段 | 延迟 |
| --- | --- | --- |
| `tasks(current_session_id, id)` | `sessions(id, task_id)` | `DEFERRABLE INITIALLY DEFERRED` |
| `tasks(latest_checkpoint_id, id)` | `checkpoints(id, task_id)` | `DEFERRABLE INITIALLY DEFERRED` |
| `sessions(continued_from, task_id)` | `sessions(id, task_id)` | 可立即检查 |
| `checkpoints(session_id, task_id)` | `sessions(id, task_id)` | 可立即检查 |
| `task_notes(session_id, task_id)` | `sessions(id, task_id)` | 可立即检查 |
| `history(session_id, task_id)` | `sessions(id, task_id)` | 可立即检查 |

## 3. 索引

初版至少建立：

- `tasks(status, updated_at)`；
- `tasks(repository_common_dir, updated_at)`；
- `tasks(worktree_path)` 在 `worktree_path IS NOT NULL` 时的部分唯一索引，禁止多个 Task 登记同一规范化 Worktree 路径；
- `sessions(task_id, started_at)`；
- `sessions(id, task_id)` 的复合唯一索引，用于同 Task 外键；
- `checkpoints(task_id, created_at)`；
- `checkpoints(id, task_id)` 的复合唯一索引，用于 Task 最新引用；
- `task_notes(task_id, created_at)`；
- `history(task_id, sequence)`；
- `session_imports(session_id, imported_at)`；
- `session_imports(session_id, sha256)` 的复合唯一索引；
- `sessions(source, external_session_id)` 在 `external_session_id IS NOT NULL` 时的部分唯一索引。

只为已定义的查询建立索引，不提前引入全文索引或复杂搜索表。

## 4. 核心模型

### Task

- 目标、范围、状态和验收条件；
- 当前 Session 和 Session 历史；Session 历史通过 `sessions.task_id` 查询，不在 Task 中重复保存数组；
- 当前步骤、阻塞、备注和关闭结果；
- Repository 路径、规范化 common-dir 身份、Branch 和 Worktree 引用；
- 最新 Checkpoint 引用和递增版本。

### Session

Session 是一次 AI 会话的引用和连续性记录，不等于完整聊天副本。`continued_from` 形成明确的继续关系；没有外部 Session ID 时使用本地稳定 ID。

`claim` 只会创建缺失的 Session，或对尚未结束的同一当前 Session 返回 no-op；不能把既有历史 Session 重新激活。`resume` 和 `claim --take-over` 的目标 Session ID 必须全局尚不存在且不同于继续来源，在同一事务中创建后再成为当前 Session。

### Checkpoint

Checkpoint 保存新 Session 恢复所需的显式事实，不保存或推断隐藏推理。数组字段在 Rust Core 中使用结构化集合，在 SQLite 中以经过校验的 JSON 保存。

### History

History 是重要 mutation 的顺序记录。它与对应业务变更在同一 SQLite 事务中提交；History 插入失败时整个 mutation 回滚，不能返回“业务成功但历史缺失”。同状态 no-op 不属于 mutation，不分配 sequence。

## 5. 事务合同

除 `task create` 外，每次面向已有 Task 的数据库 mutation 必须：

1. 从命令取得调用方最近读取的 `expected_version`；
2. 开启写事务；
3. 在事务内读取 Task，并比较当前 `version` 与 `expected_version`；
4. 校验状态、同 Task Session/Checkpoint 引用和其他不变量；
5. 写入 Task、Session、Checkpoint 或 Note；
6. 使用 `WHERE id = ? AND version = expected_version` 更新 Task，并递增 version；
7. 要求 Task update 恰好影响一行；
8. 分配并插入下一条 History；
9. 全部成功后提交，否则全部回滚。

`task create` 没有可比较的旧版本，在单一事务中插入 version 1 的 Task 和第一条 History；Task ID 冲突时整体失败。

建议写事务使用 `BEGIN IMMEDIATE`。`expected_version` 必须来自 CLI/API 请求，不能在同一写事务内读取后冒充调用方预期值。如果 version 不匹配、数据库繁忙超过 timeout 或当前 Session 冲突，返回明确冲突，不覆盖新版本；调用方必须重新读取并重新判断，不能盲目重放旧 Patch。

`session import add` 在事务外有界读取并计算 SHA-256，在事务内先执行 Task version 校验，再按 `session_id + sha256` 判断重复；重复时返回现有元数据且不写 History、不递增 version。`session import remove` 在删除连接上先启用 `PRAGMA secure_delete = ON`，再以同一事务删除 Import、递增 Task version 并写入不含原文的 History；提交后在事务外尝试 `PRAGMA wal_checkpoint(TRUNCATE)`，无法完成时返回物理擦除未保证警告，不回滚已经完成的逻辑删除。

`resume` 等需要一致读取多个表的 Query 应使用只读事务获得数据库快照。Git 观察必须在数据库写事务之外执行，避免长时间持有写锁。

## 6. Git 外部操作边界

SQLite 事务不能与 Git 命令组成同一个原子事务：

Repository 和 Worktree 的身份、持久化路径及相等判断必须使用安全文档定义的 `CanonicalPath` 和 `RepositoryIdentity`。未经规范化的输入字符串不能写入权威引用字段。Task 已有任一 Repository/Worktree 引用时，`worktree create` 必须在调用 Git 前拒绝，不能覆盖原引用。

`create/remove/adopt/detach` 必须在最终读取 Task version 和前置条件前取得按 Task ID 哈希命名的跨进程 OS advisory lock，并持有到后置观察和数据库结果确定。它只串行化同一 Task 的 Worktree 外部操作，不保存业务状态、不替代 expected version CAS；锁冲突返回 `WORKTREE_OPERATION_BUSY`。规范化 `worktree_path` 的数据库部分唯一索引负责阻止不同 Task 同时登记同一路径。

- Git 调用前立即重新观察路径和身份；此时无法证明安全则返回 `PATH_IDENTITY_UNKNOWN`，不得启动 Git；
- Git 一旦启动，无论退出状态如何都必须重新观察实际现场，不能把退出码直接等同于“未改变”；
- Worktree 创建已由现场证明成功后，才在数据库事务中保存引用和 History；数据库提交失败时不自动删除现场，返回 Worktree 路径和显式 `worktree adopt` 修复提示；
- Worktree 删除已由现场证明成功后，才在数据库事务中清除引用；数据库提交失败时保留可诊断的陈旧引用，返回错误和显式 `worktree detach` 修复提示；
- Git 非零退出且现场证明未改变时返回 `GIT_COMMAND_FAILED`；Git 已改变现场或启动后无法证明现场未改变而数据库尚未提交时返回 `PARTIAL_EXTERNAL_STATE`；
- `adopt` 只能登记 Git 已证明存在且属于指定 Repository 的 Worktree；`detach` 只能在期望路径匹配且 Git/文件系统证明 Worktree 已不存在时清除引用；
- 两个恢复命令都只修复数据库引用，不创建、移动或删除文件，并执行 Task version compare-and-swap；
- `doctor` 可以报告引用与真实 Git 现场不一致并给出建议命令，但不能擅自修复或删除。

初版不为此引入 Operation Plan；命令不得把部分完成伪装成完整成功。部分完成统一返回机器可判定的 `PARTIAL_EXTERNAL_STATE`。

## 7. Migration 与诊断

- migration SQL 随 Rust 二进制内嵌并按版本顺序执行；
- 每个 migration 在事务中执行，失败时保持原 schema；
- 初版不自动执行不可逆降级；
- `doctor` 至少执行 schema 版本检查、外键检查和 SQLite `quick_check`；
- 数据库损坏、版本过新或 migration 失败时返回明确错误，不自动重建或覆盖用户数据库；
- 备份、导出和恢复命令在出现明确需求后单独设计，不能用直接编辑数据库代替。

## 8. 后续演进

出现以下需求后再扩展：

- AI Client Hook 自动记录 Session 生命周期；
- Runtime Adapter 幂等接收可观察消息和工具事件；
- 本地 Rust Daemon 和 GUI；
- 数据库备份、导入导出和全文搜索；
- 经真实场景验证后的多 Agent、审批或可恢复外部操作模型。

除非产品边界改为跨机器共享，否则不引入 PostgreSQL 或远程数据库服务。
