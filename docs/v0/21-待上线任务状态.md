# 待上线任务状态

当前源码的Schema7、UI合同4与Schema6显式复制边界见[个人偏好与项目规则](22-个人偏好与项目规则.md)；本文Schema6内容定义待上线状态的引入格式，状态语义保持有效。

## 语义与转换

`pending_release`（待上线）表示功能开发已完成、尚未上线，便于用户识别待发布工作。它是未关闭状态，不代表已经上线、验收通过或业务完成。不新增验收状态或强制验收门槛。

| 当前状态 | 命令 | 下一状态 |
| --- | --- | --- |
| `in_progress` | `task pending-release` | `pending_release` |
| `pending_release` | `task continue` | `in_progress`（继续修改） |
| `pending_release` | 用户明确选择 `task close --outcome ...` | `closed` |

进入和返回只修改 status、version、updatedAt；保留 nextStep、当前 Session、Checkpoint、项目与 Worktree。非法来源、重复转换拒绝；过期 CAS 拒绝。待上线不直接进入 blocked；需要阻塞时先显式返回进行中，再执行原 block 流程。

关闭必须由用户明确选择，Agent 不因开发验证通过或标记待上线而自动关闭。待上线支持现有四种关闭结果；`completed` 仍要求 title、goal、scope、acceptanceCriteria 完整，其余结果仍要求 reason。关闭在同一事务中结束当前 Session，清空当前关联、nextStep 和阻塞字段。保留原有进行中直接关闭路径，不要求所有任务经过待上线。

## CLI / HTTP

以下 VERSION 和 TASK 来自明确指定的隔离库，不可直接套用正式任务。

```bash
taskctl --database /absolute/test.db --json task pending-release TASK --if-version VERSION
taskctl --database /absolute/test.db --json task continue TASK --if-version VERSION
taskctl --database /absolute/test.db --json task list --view pending-release
taskctl --database /absolute/test.db --json task list --status pending_release
```

HTTP：`POST /api/commands/task-pending-release` 或 `POST /api/commands/task-continue`。

```json
{"taskId": 1, "expectedVersion": 2}
```

命令沿用 admin/reader、Origin、CSRF、UI 合同检查，不增加 Web 业务写入口。读取支持 `GET /api/tasks?view=pending-release` 或 `?status=pending_release`。JSON envelope 仍为 `schemaVersion:2`。

CLI 关闭沿用显式 close 命令合同，不新增强制 `--yes` 校验；HTTP 关闭仍要求 `confirmed:true`。这些字段不能代替用户的实际关闭决定。

## 连续性与审计

- 待上线支持 note、checkpoint、claim 同 Session no-op、显式 take-over 和 resume；后两者不把任务改回进行中。
- checkpoint 仍要求尚未结束的当前 Session；currentSessionId 为空时 claim 拒绝，须从明确来源 resume，不重新激活历史 Session。
- update/project/components/retitle 沿用信息维护合同；update 仍禁止 status、关闭字段及 Session 等执行字段。
- 转换使用调用方 expectedVersion，在一个写事务中校验来源、修改 Task、version 加一并写一条 History；任何一步失败全部回滚。
- History 类型为 `task.pending_release`、`task.continued`，payload 为 `previousStatus` 和 `status`，sessionId 为原当前 Session（允许 null）。不改写旧 History 或 Checkpoint。

## 展示、筛选与兼容

React Web 列表和详情显示紫色“待上线”标识，状态视图独立筛选；项目关联任务使用同一展示。待上线归入“未关闭/最近全部”，不归入“进行中/已关闭”。沿用现有分页列表，不新增统计 API 或仪表盘。

源码数据库为 **Schema6**，只扩展 tasks.status CHECK 枚举，不推断或批量更改现有任务状态。普通连接不升级 Schema5。

```bash
taskctl --database /absolute/private/new-schema6.db --json --yes database import-schema5 --source /absolute/quiescent/schema5.db
```

显式复制要求源已停写、目标不存在、私有本地目录；按冻结 Schema5 校验源布局，复制全部14表及自增高水位，逐字段比对与 typed hash 校验，保留 Task/Project 版本、Session、History、项目资料和原始 payload，不访问历史外部路径。失败不发布目标，不升级源库。Schema2/4 显式复制入口的目标同为当前 Schema6。

UI API 合同为 **3**（包格式仍为1），新版 React 请求携带合同3。旧合同1/2 UI 包不再适配：不能将旧 manifest 改号冒充兼容；候选 taskd 拒绝旧包并在冷启动时使用新版内嵌回退，旧页面请求被明确拒绝。`web-legacy-readonly` 与旧原生 UI 是历史实现，不作为 Schema6 发布入口。构建后显式同步 `web/dist` 到 `crates/server/web-readonly`，再编译候选 taskd。

Windows 包/启动器只接受 Schema6，不通过普通更新跨 schema，不将旧二进制回退到新库。正式库迁移、部署、重启和远程写入必须另获授权；恢复旧版本需要对应旧库和独立安装，不保证新状态可逆导回 Schema5。
