# V0 项目与上下文复用

## 1. 当前交付与安全边界

#34 当前主线为**项目功能交付**：整合与回归 → 创建项目/登记源码/关联任务/项目查询/上下文流程验收 → 项目管理页面 → 经授权的迁移与发布。已实现 **Project、任务归属/组件范围、Component、Repository/SourceRoot、CLI、项目管理 HTTP/页面、任务上下文增补与显式源码导航**。源码登记可选，不是创建项目的前置。缓存复用、Pi到Rust桥接及自动注入暂缓，不是本轮项目功能交付条件。人工验收见 [第17篇](17-项目管理验收.md)，自动化通过不等于真实浏览器/人工验收或已部署。

**当前开发构建的 SQLite Schema 为 4，JSON envelope 仍为 2。只在空库初始化，拒绝 Schema 2 正式库及前批 Schema 3 开发库，不隐式附加新表。** 测试使用临时库，开发命令必须显式提供 `--database`。已提供含活动任务的 Schema 2 停写快照显式复制入口 `database import-schema2`，见 [第18篇](18-Schema2到4迁移与隔离演练.md)；尚未在正式库执行或授权切换。不要用本构建覆盖全局 CLI、Hook 或运行中的 taskd，也不要直接运行 Windows 本地更新脚本切换正式服务。旧库继续由旧构建使用。

本功能不自动创建项目、扫描所有仓库、领取任务、采纳 Worktree、启动服务或授予执行权限。Mailroom 是一个业务项目，backend/android 是组件；不是按每个技术目录建立一个 Project。

## 2. 项目身份与引用（已实现）

- Project 使用数据库生成的正整数 `id`（AUTOINCREMENT），不可修改，删除后不复用；当前不提供删除命令。
- 人类项目引用为 `##3`，Task 保持 `#34`。JSON 中 `id/projectId` 仍是整数，未关联时为 `null`。
- 在项目参数位置接受裸正整数、`##数字` 或唯一名称。`#数字` 不会解析成项目；Task 参数也拒绝 `##数字`。
- 项目名称先 trim，再 NFC；显示名保留大小写，唯一键仅折叠 ASCII A–Z。非 ASCII 大小写保持区分，不使用 locale、拼音、相似度或文件系统规则匹配。
- 名称长度 1–120 Unicode 字符，禁止控制字符、纯 ASCII 数字以及以 `#` 开头的名称，以免与引用冲突。内部空格不合并。
- 唯一范围是当前 Steward 数据库。名称冲突返回 `CONSTRAINT_VIOLATION`，不存在返回 `NOT_FOUND`；不自动建立项目或旧名称别名。
- 改名不修改项目 ID、所属任务、Task version、Session 或 Worktree。

`ProjectView`：`id/name/revision/createdAt/updatedAt`。修订号初始为 1，改名要求调用方刚读取的 `expectedRevision`。错误 `VERSION_CONFLICT` 带 `entityType=Project`、`projectId`、`expectedRevision/currentRevision`；不伪装成 Task version。

## 3. CLI 合同（已实现）

以下命令均使用不存在的隔离示例库，项目编号由创建返回值确定，不代表正式项目记录。Shell 中含 `#` 的引用必须加引号。

```bash
# 实际使用时替换为隔离库的绝对路径。
taskctl --database /absolute/demo.db project create --name Mailroom
taskctl --database /absolute/demo.db project show '##1'
taskctl --database /absolute/demo.db project list --after 0 --limit 50
taskctl --database /absolute/demo.db project rename '##1' --name 收发室 --if-revision 1
taskctl --database /absolute/demo.db project history '##1' --after 0 --limit 50

taskctl --database /absolute/demo.db task create --project 收发室
taskctl --database /absolute/demo.db task list --project '##1' --fields id,title,projectId
# version 必须来自最新 task show；这里 1 仅为示例。
taskctl --database /absolute/demo.db task project '#1' --project '##1' --if-version 1
taskctl --database /absolute/demo.db task project '#1' --clear --if-version 1
```

- `project list` 按 ID 升序，`after` 为最后项目 ID；`project history` 按 revision 升序，`after` 为最后 revision。上限默认 50、允许 1–200，返回 `hasMore/nextAfter`。这是明确的 keyset 分页，不承诺跨请求静态快照。
- `task create` 的 JSON 输入可包含 `"project":"Mailroom"`。若同时给 CLI `--project`，两者必须在同一写事务中解析为同一个项目，否则创建失败；没有项目时 `projectId=null`。
- `task project` 必须给 `--project` 或 `--clear`，不可同时给。清除关联不删除项目。
- `task components <task> --component frontend --component backend --if-version VERSION` 显式选择当前项目中的组件；`--clear` 清空范围。组件参数按名称解析，不能引用其它项目的组件。不自动创建组件。
- Task 的 `componentIds` 是升序、不重复的 ID 数组（未选择时为空）；show/list/context/resume 均通过当前数据库关系派生，不在 Task JSON 中保存第二份可编辑数组。
- Task 列表新增 project 筛选及 projectId/componentIds 字段投影。游标摘要绑定解析后的项目 ID；不同项目不能复用游标，同项目改名后用 ID 可继续分页。筛选合同扩展后，旧构建生成的游标应重新查询，不持久化为状态。
- HTTP `GET /api/tasks` 同样接受 `project` 筛选；URL 中 `##1` 应编码为 `%23%231`，避免作为 fragment。项目管理 HTTP/GUI 见下一节；全局 `steward_task` 的项目参数尚未扩展，不修改已安装扩展。

### 项目管理 HTTP / 页面（开发实现）

HTTP 的 Git source resolve/context 对所有角色使用同一读取边界：`worktree` 先做不访问文件系统的词法校验，拒绝 UNC、设备前缀、ADS 和父级跳转；再仅从登记 Repository 的当前 `git worktree list` 输出选择本机 checkout，未匹配前不解析请求路径或其它候选路径。支持登记仓库的 linked checkout；不自动选择默认工作区、独立 clone 或目录别名。请使用清单中的路径拼写（兼容盘符大小写、分隔符和 Windows verbatim disk 形式，不通过文件系统补全其它大小写/别名）。匹配后仍验证 live Repository/SourceRoot 身份；这不防御有权篡改本机文件系统/Git 元数据的进程，也不授予 Worktree 执行权限。CLI 和管理员显式源码登记合同不变；网络 Git 登记不能用于这一 HTTP 本机 checkout 查询入口。

这两个 HTTP 读操作的同步 worker 共享 10 秒 Git 读取预算；请求 Future 被丢弃时设置取消标志，下一检查点或正在运行的 Git 进程观察到后结束。stdout/stderr 在读取中分别限于 8 MiB/64 KiB；超时、取消或溢出以 `GIT_READ_LIMIT`（HTTP 503，不自动重放）失败。Windows 子进程暂停创建、先加入 kill-on-close Job 再恢复，Unix 用独立进程组并保留 leader PID 到清理，终止后代/回收直接子进程后结束 worker、释放并发槽。普通 Worktree 写流程不套用这一读取消作用域。10 秒是触发取消/终止的预算，不是操作系统清理、挂起原生文件 I/O 或恶意进程沙箱的硬保证；客户端断开是否立刻丢弃处理 Future 取决于 HTTP 栈，独立预算始终保留。

同一 `run_read` 现也用于 HTTP Task `context`、`worktree-status`（及同组只读资源）与只读 `doctor`；这些路径的通用 Git 查询不再落入无作用域的 `Command.output()` 分支。取消检查在 worker 开始业务读取前执行；每次请求有独立预算，写命令仍使用原 `run`。保留原有 Task context/doctor 的诊断合同：Git 不可用时可以返回任务/数据库快照及观测失败告警或 issue，不把未知状态标作 clean，也不强行统一为项目导航的 HTTP 错误。该 Git 预算不提供整个 HTTP 操作、SQLite 查询或原生文件 I/O 的硬时间上限。

页面入口为同源 `/` 工作台顶部“项目管理”，不是新增独立前端服务或 `/projects` 页面路由。提供项目分页/创建/改名、组件新增、Git/普通目录源码登记与解除、源码导航；任务侧增加项目归属、组件范围、创建时项目输入及项目筛选。没有项目删除、组件删除/改名或自动扫描/绑定。所有文件路径属于服务所在机器，登记不上传/复制源码。

查询（admin/reader均可用，沿用既有鉴权/Host/Origin边界）：

| GET | 合同 |
| --- | --- |
| `/api/projects?after=0&limit=50` | ID升序、keyset分页；limit 1–200 |
| `/api/projects/{ref}` | 项目快照；路径中的名称/##引用须URL编码 |
| `/api/projects/{ref}/history?after=0&limit=50` | revision升序历史 |
| `/api/projects/{ref}/components`、`/sources` | 组件/源码及所属项目快照；沿用200项上限 |
| `/api/projects/{ref}/sources/{sourceId}?worktree=...` | 当前路径解析；Git须显式绝对工作区路径 |
| `/api/projects/{ref}/context?sourceId=...&worktree=...&budgetBytes=8000` | 有界只读文件导航，不开放file/dependency参数或源码正文读取；预算1024–64000 |

写入统一使用 `POST /api/commands/{command}` 的严格JSON，reader在解析请求体前被拒绝，沿用请求体上限及业务并发槽位；不自动重试。

| command | 必需/可选字段 |
| --- | --- |
| `project-create` | name |
| `project-rename`、`project-component-add` | projectId、expectedRevision、name |
| `project-source-add` | projectId、expectedRevision、location；component可选现有组件名称 |
| `project-source-remove` | projectId、expectedRevision、sourceId、confirmed=true |
| `task-project` | taskId、expectedVersion、confirmed=true；project引用与clear=true二选一，缺失两者或同时给出均拒绝 |
| `task-components` | taskId、expectedVersion、components名称数组（空数组清空）、confirmed=true |

location严格区分 `{"kind":"git","worktree":"绝对路径","relativePath":"."}` 与 `{"kind":"directory","path":"绝对路径"}`，未知字段拒绝。项目mutation不夹带Task版本；Task归属mutation不使用Project修订。前端冲突展示对应实体最新快照，保留输入，只在用户选择“采用此版本，重新审查后提交”后更新该实体的CAS基准；写入结果未知时禁用提交、提供只读核对入口，不自动重放。迟到刷新不得关闭新打开的表单。原生 dialog `close` 事件是排队触发的；监听器发现 dialog 已重新打开时忽略旧事件，不清空新表单或丢弃其待完成提交。正常关闭仍清空当前状态并处理延后的 SSE 刷新。

项目选择转为稳定`##ID`筛选，项目条件随任务视图/搜索/分页传递，切换项目先清空旧行、游标、更多按钮与详情选择；请求失败保留新筛选但不保留旧范围，恢复查询不得跨项目拼页。清除项目筛选不清除任务归属。迟到的组件查询必须同时匹配表单意图代次和任务快照代次，不得覆盖后来打开或关闭过的新表单。项目页的SSE刷新保留已加载范围，打开表单时延后刷新。Task复制上下文包含project、componentIds、notesSinceCheckpoint及截断提示。源码上下文以只读文本展示目录、Git观察及文件导航，不把导航当执行权限。

UI/API兼容合同仍为1：`GET /api/access` 新增 `projectManagement:true` 能力声明。新UI仅在声明存在时启用项目入口、筛选和创建参数；旧后端未声明时继续原任务功能，不向其发送新增项目字段/命令。该能力不是授权，写操作仍校验admin。三文件UI包合同不变；当前Schema4后端不能直接替换Schema2正式服务，不能以“纯UI发布”绕过后端迁移。

## 4. 归属与事务（已实现）

新增 `projects` 与 `project_history` 表，Task 增加可空 `project_id` 外键和 `(project_id,updated_at,id)` 索引。项目只是业务归属，不取代现有 Task 的 Repository/Worktree 四字段合同。

- 一个 Task 当前可关联一个主项目，允许先创建再关联。
- 创建项目和第一条 `project.created` History 同事务；改名和 `project.renamed` History 同事务，每个 revision 唯一。
- `project.created` payload 为 `name`；`project.renamed` 为 `previousName/name`。不把项目变更塞进某个任意 Task 的 History。
- Task 归属变更在 `BEGIN IMMEDIATE` 中先校验 Task version，再解析项目、修改归属、递增 Task version、写 `task.project_changed` History；payload 为 `previousProjectId/projectId/previousComponentIds`，项目 ID 允许 null。实际更换或清除项目时，在同一事务中清空旧组件范围；同项目 no-op 保留范围。创建 Task 的 `task.created` payload 增加 `projectId`。
- 同值请求仍先检查 CAS，再返回 no-op，不写 History。History 失败则业务变更整体回滚。
- 组件范围变更使用 Task CAS、`task.components_changed` History（previousComponentIds/componentIds）。`task_components` 的复合外键同时保证 Task 和 Component 属于同一项目；失败整体回滚。项目 revision 不因任务选择组件而改变。
- closed Task 仍只允许 retitle，不通过项目关联或组件选择绕过既有闭合边界。
- 关联操作不修改 Task 状态、当前 Session 或 Worktree，也不改变 Project revision。纯读取不修改任何聚合版本。

## 5. Task context 增补（已实现）

`task context` 的同一读事务中取得 Task、Project、最新 Checkpoint、当前 Session 与检查点之后的 Notes；提交读事务后再观察已登记的 Git Worktree。

新增 JSON 字段：

- `project`：ProjectView 或 null；
- `notesSinceCheckpoint`：检查点之后的新 Notes，按 History sequence 顺序；
- `notesTruncated`：是否仅包含最新 50 条。

检查点边界通过 `checkpoint.saved` History 的 checkpointId 定位，不依赖同毫秒时间比较，避免时钟回拨遗漏新 Notes。无检查点时从任务历史起点读取。超过 50 条返回 `CONTEXT_NOTES_TRUNCATED` 警告，完整内容通过 `task notes` 显式读取；此处是条数限制，不是已实现的 token 预算。

Project、Checkpoint 与 Notes 仅提供带来源上下文，不授予执行权限。未登记 Worktree 时 `worktreeStatus=null`，不能因为有关联项目而声称已核实 Git。`resume` 的状态变更合同不变，本次没有将项目/Notes 增补扩展到 resume 响应。

## 6. 组件、源码根与候选定位（已实现）

业务侧 `Project → 可选 Component`，代码侧 `Repository → Worktree`，通过 `SourceRoot(repositoryId,仓库内相对路径)` 连接。支持一项目多仓库、一仓库多项目、共享目录；SourceRoot 不保存默认 Worktree，实际路径必须实时解析。非 Git 来源使用显式 directory-only 关联。

### CLI

以下 `REVISION/VERSION` 必须替换为刚读取的项目修订/任务版本；源路径必须存在。数字 SourceRoot ID 由添加返回值确定，不能假定正式项目已经有示例编号。

```bash
taskctl --database /absolute/demo.db project component add '##1' --name backend --if-revision REVISION
taskctl --database /absolute/demo.db project component list '##1'
taskctl --database /absolute/demo.db project source add '##1' --component backend --repo /absolute/repo --path services/api --if-revision REVISION
taskctl --database /absolute/demo.db project source add '##1' --directory /absolute/non-git-documents --if-revision REVISION
taskctl --database /absolute/demo.db project source list '##1'
taskctl --database /absolute/demo.db project source resolve '##1' 1 --worktree /absolute/selected-worktree
taskctl --database /absolute/demo.db project source remove '##1' 1 --if-revision REVISION
taskctl --database /absolute/demo.db project here --directory /absolute/selected-worktree/services/api
# 可按项目限制候选范围，不自动选中项目或任务。
taskctl --database /absolute/demo.db project here --directory /absolute/selected-worktree --project '##1'
taskctl --database /absolute/demo.db task components '#1' --component backend --if-version VERSION
```

### 登记与路径约束

- 新增 `components/repositories/source_roots/task_components`。组件名沿用项目名规范，但唯一范围仅为所属项目；SourceRoot 可不指定组件。
- `--repo` 是明确提供的已有 checkout 或其子目录，必须同时给 `--path`；解析为 checkout 根，不将输入子目录当仓库根。裸仓库不支持。
- 相对路径使用 `/`，根目录用 `.`。拒绝绝对路径、`..`、中间 `.`、空分量、反斜杠、冒号、控制字符、`.git` 及尾随空格/点的歧义分量。不通过规范化把越界输入变成合法输入。
- 源必须是已有目录；canonical 后仍在 checkout 内且属于同一 Git common-dir。越界 symlink/junction、嵌套独立仓库和子模块必须单独关联其仓库，不能继承外层项目根。
- `--directory` 与 Git 参数互斥。directory-only 来源若自身或祖先有 `.git`（包括失效链接）或裸仓库标记即拒绝；后续出现 Git 标记会使其失效。
- Repository 在显式 source add 中按 common-dir 原生对象身份去重，独立 clone 不按 remote/名称合并。同仓多个组件/项目及多个 Worktree 共享 Repository ID。
- 保存的 canonical common-dir 与原生对象身份仅是本机登记时的校验基准，不是当前 Git 状态。每次 resolve/here 都实时复核。观察到原生身份不匹配、路径丢失或原登记路径移动时拒绝，不静默重新绑定；持久化原生 ID 不是跨进程身份连续性证明（详见下文），当前尚无 Repository 重定位/修复命令，需要后续显式核对方案。
- `component/source/here` 不读文件正文、不观察或保存 HEAD/dirty/服务/测试状态；在 dirty Worktree 解析路径并不意味着其源码事实仍有效，内容校验留给下一阶段。

### 事务与读取语义

- 添加组件、添加/移除源使用 Project revision CAS，并同事务写 `component.created/source.added/source.removed` History。Repository 首次创建与 source.added 一起提交；失败无孤立登记。重复名称或重复源关联报约束冲突，不消耗 revision。
- SourceRoot 通过复合外键约束组件与项目一致。组件上限和每项目源码根上限各 200；全局候选源码扫描最多 2000，超限明确报错，可指定 project 缩小范围。Repository 登记/去重扫描上限 2000，达到上限后只允许关联已有 Repository。
- Git 子进程均在 SQLite 写事务之外；事务内仅做短时文件对象身份复核。提交后再核对来源，发生竞争返回 `SOURCE_OBSERVATION_CHANGED` 警告，明确元数据已保存而现场未能复核。任何登记都不承诺 Git/SQLite 原子快照。
- `source list` 仅返回登记及 common-dir 定位引用，`liveStateObserved=false`；不把列表当现场。Git `source resolve` 必须提供 Worktree，directory-only resolve 则禁止 Worktree 参数。
- `source remove` 仅删除当前项目的一条关联，可在目录已丢失时使用；不删除源码、组件、Repository 行、Git 登记或 Worktree。
- `project here` 在读事务取快照，释放后观察文件系统/Git。返回所有候选及 `matchedBy`：`source` 为目录命中，`repository` 为同仓相关，`ancestor` 为非 Git 父目录关联。源命中优先，同为命中时更深的源码根优先，其余保留为明确候选；`selectedProjectId` 恒为 null。
- 参与当前目录匹配但复核无效的来源不作为候选，返回带 projectId/sourceId 的 `SOURCE_UNAVAILABLE` 警告。全局注册表读取失败或当前目录身份无法证明时整体拒绝，不能假装没有项目。
- `task here` 保持原有 Worktree 登记语义，不自动把 project here 的候选转成任务归属。Project/组件/共享源码不是目录排他所有权，也不是执行授权。

## 7. 显式来源上下文（第四阶段首批，已实现）

```bash
# 使用开发构建及隔离库。SourceRoot ID 必须取自当前项目登记结果。
taskctl --database /absolute/demo.db --json project context '##1' --source 1 --worktree /absolute/selected-worktree
# 只有 --file 明确指定的文件才返回正文片段。不要请求无权读取或含密钥的文件。
taskctl --database /absolute/demo.db --json project context '##1' --source 1 --worktree /absolute/selected-worktree --file src/main.rs --dependency Cargo.lock --budget-bytes 8000
```

- `--file` 路径相对于已解析 SourceRoot；`--dependency` 相对于所选 checkout 根（非 Git 来源则为 SourceRoot），仅返回指纹，不返回依赖正文。参数可重复；禁止 traversal/绝对路径/`.git`，不自动遍历源码树。
- 默认导航发现 SourceRoot 到 checkout 根的 README/CODEMAP 与固定常见配置/锁文件名称：Cargo.toml/Cargo.lock、package.json/package-lock.json/pnpm-lock.yaml/yarn.lock、go.mod/go.sum、Directory.Build.props/global.json。非 Git 来源只检查自身这些文件。
- 规则导航检查 SourceRoot 到文件系统根的 AGENTS.override.md/AGENTS.md/CLAUDE.md，以及显式文件/依赖的目录祖先。这里只发现已知文件名，不解释条件规则、不替代宿主已加载规则、全局规则或其它规则文件格式。缺失规则/配置文件也纳入内部指纹，后续出现会改变指纹。
- 返回 entries 的路径、类型、SHA-256、完整文件字节数；仅 requested 条目有 snippet/snippetTruncated。正文是来源数据，不授予执行权限；不把文档陈述提升成已验证架构事实。
- 输出 `contextVersion=3`，同时纳入来源指纹（v2增加override发现；v3保留跨两轮观察的活跃身份并显式标记持久记录的连续性缺口，旧版本观察指纹不沿用）；发现算法、指纹覆盖或派生语义改变时须升版。条目 evidence 为 `file-navigation-v1`（路径/文件元数据）或 `source-prefix-v1`（已核对原文的 UTF-8 前缀），整体恒为 `semanticFactsVerified=false`。规则文件正文里的“已验证”陈述也不会改变这个等级。
- 观察指纹不包含渲染预算。相同指纹在不同预算下可以返回不同长度片段；不能仅按 fingerprint 缓存整个响应。未来原文片段键还必须包含派生版本、起止字节范围/输出约束；未知版本拒绝复用。
- `fingerprint` 绑定 Project/revision、SourceRoot、实际根与 common-dir 原生身份，以及本次已观察文件的路径/原生对象身份/内容 hash/缺失状态、Git HEAD/分支/status 指纹。不同项目、Worktree、内容变化或观察到的原生对象 ID 变化会改变指纹。跨进程或旧快照释放后的 ID 复用不能仅靠此摘要排除，所以它不是历史身份连续性证明。
- 文件与登记均前后复核；观察到变化就报错，不能静默返回旧片段。拒绝文件/目录别名与 symlink/junction 越界、嵌套仓库边界，非 Git 来源也不能穿入后出现的嵌套 Git 仓库。
- Git 来源新增前后两轮 porcelain-v2 现场观察；`gitStateObserved=true`，`git` 包含 head（未提交仓库为 null）、branch（detached 为 null）、dirty（tracked/untracked 变化）、hasIgnored、statusSha256。HEAD/分支/status 改变均令指纹变化；两轮观察不一致即失败。非 Git 来源仍为 gitStateObserved=false、git=null。
- status 命令禁用 optional locks、fsmonitor 和 untracked cache，显式包含 untracked、ignored 与 submodule 状态，不执行 Hook 或 Git 写操作。status 子进程使用流式 8 MiB stdout / 64 KiB stderr 上限和默认 10 秒终止预算；HTTP 读入口把所有 Git 查询纳入同一个预算（见上）。原始 status 路径不回传，仅输出摘要。
- **没有持久缓存，恒为 `reuseAllowed=false`、`atomicSnapshot=false`。** 相同 status 不证明未选取文件的内容不变（尤其 ignored 文件）；指纹仍不覆盖全部依赖及宿主/工具环境。前后检查不是 SQLite/文件系统原子快照；Task CAS、Session、授权、服务和测试不能从此输出恢复，后续执行时仍需实时核实 Git。
- `reuseBlockers` 始终包含 DEPENDENCY_COVERAGE_UNKNOWN/HOST_RULES_UNOBSERVED/ENVIRONMENT_UNOBSERVED；按现场再加 NON_GIT_SOURCE、UNBORN_HEAD、DIRTY_WORKTREE、IGNORED_CONTENT_UNCOVERED。即使 Git clean，未知覆盖也不转成复用许可。
- `budgetBytes` 限制 compact JSON **data 对象**的 UTF-8 字节数，默认 8000、范围 1024–64000；不是模型 tokens，也不包含 envelope、warnings、缩进或终端渲染。先保留规则导航、显式请求、依赖，再普通导航；元数据超限从末尾省略并返回 omittedEntries，基础元数据也放不下时报错。片段按实际 JSON 转义大小和 UTF-8 边界裁剪，明确 snippetTruncated。
- 最多 64 个显式文件/依赖、256 个候选路径；单文件最多 1 MiB、每轮观察合计最多 8 MiB，超限或必需文件缺失即失败。自动导航不会隐式降级成未校验摘要。
- 只读既有项目登记，不推进 Project/Task version，不创建任务或 Session，不写来源正文/指纹到正式库、Task History 或新缓存目录。Schema 保持 4。

`ExistingPathIdentity` 是活跃观察，Linux用Arc共享O_PATH句柄，不能反序列化；`ExistingPathIdentityRecord` 只保存原有canonical_path/object.first/object.second，严格拒绝未知字段。活跃观察序列化仍投影同一记录格式，不包含句柄或进程地址，因此既有开发记录/对象摘要格式不变。`observe_recorded_identity` 只取得与记录匹配的新观察，不能恢复旧进程的pin。`Observed`保留首轮文件身份直到第二轮结束；宿主规则核验也保留首轮身份，并比较缺失规则的最近存在祖先。pin数量受既有候选/规则上限限制，作用域结束自动释放。

`PERSISTED_IDENTITY_CONTINUITY_UNPROVEN` 恒列入项目上下文blocker：新观察前的跨进程/跨调用间隔仍可能发生原生ID复用，持久记录不能冒充活跃快照。非Linux平台不能继承O_PATH保障；文件/Git/SQLite仍非原子快照。该限制不因双次读取、摘要相等或测试通过而解除。

每轮读取内按文件父目录复用一次边界核验，第二轮清空集合重新核验，不跨调用缓存；所有文件仍读两遍并复核原生身份。`observation` 返回 candidatePaths/fileReads/boundaryChecks（只统计文件读取环节，不代表全部 Git 子进程数）。Windows 合成同目录 8 文件测试将该环节的目录核验由逐文件两轮 16 次降为 2 次；一次并发测试中的端到端观察为 3730 ms、data 为 3000 bytes，不能外推实际项目节省或宣称端到端提速。

这批提供可审计的现场来源入口，不宣称缓存命中、token 节省或完整依赖/环境失效能力。新增 Git 证据也有成本，仍需实际项目隔离基准。

## 8. 后续优化方向（本轮暂缓）

### 事实与缓存

- 项目登记与 Task 状态：Steward SQLite 权威。
- 规则：继续使用现有 AGENTS/CLAUDE 及宿主规则加载，不复制成新规范。
- 项目事实：现有文档/源码为来源，缓存只保存可重建的导航和片段。
- 缓存元数据：项目/组件/仓库/Worktree 范围、来源路径/章节/hash、核实基准 commit、依赖、核实者和时间、证据等级。
- 来源/规则链/版本/路径身份变化即失效；dirty 保守降级到实时读取，不复用 clean 源码结论。公共库、根配置和锁文件属于依赖范围。
- hash 相同不证明文档语义正确；无法核实的内容只能标为文档导航。
- 环境能力提示按主机/宿主/工具配置和版本短期隔离，到期、重载或配置变化即失效。
- Git、Task CAS、Session、授权、服务状态与测试结果必须实时核实，历史记录不能变成项目现状。
- 优先显式宿主无关入口；Pi 后续只注入短导航，复用已加载 contextFiles 和工具清单。自动导航约 500 tokens、按需片段约 2000 tokens 是待测预算，不是当前完成的能力。

### 允许持久复用前的覆盖门槛（设计，尚未实现）

- 先按条目区分“已知路径导航”“原文片段”“经验证的语义结论”；不能用文件 hash 把导航升级为语义事实。
- 每项须有版本化派生算法、来源/缺失状态、完整适用规则与依赖清单；显式 --dependency 只表示已观察，不能自行宣告依赖闭包完整。
- 宿主须提供实际加载规则/配置及工具能力的可核对版本身份，不能直接缓存环境变量全集或密钥；未知宿主、缺失配置、失效能力一律阻止复用，而非套用本机默认值。
- dirty、未提交 HEAD、路径对象变化、依赖/规则/环境变化及算法版本变化应保守失效；相同 status/HEAD 不替代文件核验。缓存只是可删除派生物，不能包含任务当前权限或动态状态。
- 当前入口尚未满足这些门槛，不新增“手工 complete=true”或忽略 blocker 的旁路。

### 宿主规则/环境证据输入合同（基础库/应用绑定与 Pi 实验采集已实现，尚未贯通）

后续证据由当前宿主适配器提供，不把任意用户 JSON 的 complete=true 当证明，也不读取整个环境变量集。

| 证据 | 最小绑定与核验 | 缺失/失效行为 |
| --- | --- | --- |
| 宿主实例 | 宿主名称/版本、当前实例与 Session、采集时间/失效时间、适配器协议版本；和当前请求核对 | 未知版本、实例/Session 变化、过期或时钟异常均拒绝复用 |
| 实际规则 | 宿主实际加载顺序、每份规则的路径/对象身份/加载内容 hash，以及作用范围/条件和被检查但缺失的规则 | 只发现 AGENTS/CLAUDE 名称不够；重新核对文件和加载清单，缺项不猜测 |
| 工具能力 | 仅所需工具的名称/版本、配置指纹、可用/不可用/未知及最近核验时间；不保存配置正文或凭证 | 工具重载、版本/配置变化、过期或未知状态使对应条目失效 |
| 条目依赖 | 派生器版本、目标/组件/Worktree、完整输入集合和缺失状态；原文前缀只证明所选字节，语义条目另须可审核证据 | 显式 --dependency 列表不是闭包证明；未知语言、动态配置/条件未覆盖时保留 blocker |

已实现的基础库：

- `steward_core::HostEvidence` 使用 protocolVersion=1，拒绝未知字段（包括 complete/trusted 旁路）。HostBinding 包含 host/hostVersion/instanceId/sessionId/scopeSha256；预期绑定必须由调用方从当前请求独立取得，不能复制报告自己的绑定冒充核验。它不是 Session 归属认证或 Task CAS。
- 有效期以毫秒时间戳表达，最长五分钟；未来采集、到期、过长有效期均拒绝。`assess_host_evidence` 使用调用方实时 clock，在文件 IO 前后重验并拒绝时钟回退；不会从报告取得当前时间。
- rules 保留报告顺序，每项为规范绝对路径及内容 sha256/objectSha256 对，双 null 表示报告中明确的缺失项。对象摘要是本机 git-adapter ExistingPathIdentity 序列化后的 SHA-256，不是 mtime。拒绝重复路径、traversal、非法摘要、文件别名、内容变化、观察到的原生对象变化及缺失文件新出现；报告产生到本次首轮观察之前的身份连续性不由摘要证明。
- tools 仅收名称、available/unavailable/unknown、版本和配置摘要；available 必须有版本与配置摘要。这里只校验声明，不执行工具、不证明能力可用。每份报告共享有效期，不声称覆盖工具独立探测时间。
- 最多 64 个规则、64 个工具；规则文件双读，每文件上限256 KiB、每轮合计4 MiB，超限失败。传输接入方还须在反序列化前限制输入大小（建议128 KiB）；当前没有 CLI 输入入口。
- `HostEvidenceAssessment` 仅输出报告摘要、核验文件/缺失路径数量及自报工具数量，不回传文件路径、规则正文或配置正文，不写数据库/History/缓存。恒为 hostClaimVerified=false、reuseAllowed=false；空清单、通过校验或哈希一致都不解除 project context 的 blocker。
- 应用层新增 `HostContextRequest`（Task 引用/expected version/Session/source/context 参数）与独立 `HostInstance`（宿主运行时名称/版本/实例）。`Service::host_context_binding` 不接收报告，自 SQLite 读取当前 Task/Session 并从 Task 取得项目；拒绝无项目、closed Task、旧 Task version、非当前/已结束/属于其它任务的 Session，以及跨项目 source。已选择组件时拒绝其它组件的 source；未指定组件的共享根仍可显式请求。
- scopeSha256 纳入 bindingVersion=1、本机数据库对象身份、Task ID/version/组件、Session ID/startedAt、项目、SourceRoot、实时 contextVersion/fingerprint，以及请求 files/dependencies/budget。同记录的另一数据库、其它 Worktree、不同预算/文件请求不能套用同一绑定；相同请求可在有效期内得到相同绑定，它不是一次性授权 token。
- `Service::assess_task_host_evidence` 使用系统时钟，独立构建绑定、调用底层文件复核，再重新构建完整绑定并检查最终有效期；Task/Session/来源/Git/内容/请求变化时拒绝。Git/文件 IO 不在 SQLite 事务中执行，仍不承诺原子快照。实际报告采集前可调用 binding 方法取得请求范围，核验时必须重新计算，不能直接把报告绑定当预期值。绑定及前后重算会重复执行实时 context 观察，增加文件/Git 成本，本批不宣称提速。
- 应用调用不 claim/adopt、不写 Task/Project/Session、不卡住长写事务。它绑定显式源码观察请求，不把请求选择的 checkout 自动改成 Task 登记 Worktree，也不是执行授权。低层 assessor 保留给明确提供独立绑定/时钟的调用方；适配器应优先用应用入口。
- 当前模型尚未表达/验证完整条件作用域、真实宿主加载、工具探测或依赖闭包。这些仍需适配器与条目级证据实现，不能把基础库通过误报为完整合同已实现。

宿主报告与本地文件复核是不同证据层：哈希匹配只能证明观察的字节一致，不能单独证明该进程实际加载过它，也不能证明规则语义正确。基础测试已覆盖绑定变化、规则加载后修改、缺失文件出现、同内容对象替换、过期/时钟回退及未知字段拒绝；隔离 Pi 0.85.1 的实际加载/工具目录 API 已验证，但真实会话完整加载链、工具配置重载及 Rust 贯通仍待测试；当前 ENVIRONMENT_UNOBSERVED/HOST_RULES_UNOBSERVED 不解除。

- `crates/application/src/host_context_tests.rs`：应用独立绑定、复制数据库/跨任务/Session/项目/linked Worktree 拒绝、组件和预算范围、核验中 Task version/文件变化及最后阶段过期/时钟回退。
- `crates/core/src/host_evidence.rs` 与 `crates/application/tests/host_evidence.rs`：宿主报告协议/绑定/有效期、文件双读与变更拒绝、缺失项、输入边界，校验通过仍不升级为可信宿主或复用许可。
- `crates/core/src/projects.rs`、`sources.rs`：名称 NFC、ASCII 大小写、保留语法、中文与引用隔离；源码相对路径拒绝越界和跨平台歧义。
- `crates/application/tests/sources.rs`：合成两项目/monorepo/多仓/共享目录、临时 linked Worktree、独立 clone、目录别名、越界链接/嵌套仓库、原生对象替换失效、Project/Task CAS与History回滚及组件范围外键。Windows 实测目录别名使用 junction；其它 OS 尚待 CI 验证。
- `crates/application/tests/project_context.rs`：导航无正文、规则新增/同内容对象替换指纹变化、UTF-8/JSON 转义预算与显式省略、输入上限/越界拒绝、两项目与 linked Worktree 隔离、同 HEAD 的当前 dirty 片段、根锁文件/显式共享依赖及依赖局部规则变化；unborn/detached/空提交/staged Git 证据，未观察 ignored 内容变化的复用拒绝，单轮父目录核验合并与跨调用新仓库边界拒绝。
- `crates/application/tests/projects.rs`：两项目归属隔离、名称唯一、分页、改名稳定 ID、CAS、并发改名、History 原子回滚、外键、ID 不复用、新 Notes 及截断。
- `crates/cli/tests/projects.rs`：真实 CLI 名称/编号引用、任务创建/筛选/关联/清除、显示及旧 Schema 拒绝。
- `crates/application/tests/migration.rs`：旧归档迁入当前新库后 projectId 留空，原字段/History/BLOB/序列不变。

以上自动测试主要是合成项目测试，不是实际 Steward/Mailroom 工作副本的完整事实缓存验收。本批已用合成项目和临时 Git 仓库验证多仓/monorepo/共享目录及 Worktree 路径隔离；若后续恢复事实复用优化，再在两实际项目隔离副本验证内容、依赖和环境失效，并测量重复探索调用、上下文体积及耗时；这些不作为本轮项目管理功能交付前提。正式库迁移、全局安装、服务部署和人工验收未执行。

### 实际源码抽样隔离实验

在 Windows 本机以临时新库和临时 Git 仓库执行；只复制选定当前文件，不复制正式数据库、密钥、业务数据或整个工作树，不运行两个项目的业务代码。Steward 抽样为 Cargo.toml/Cargo.lock/crates/core/src/sources.rs；Mailroom 抽样为 backend-rust/Cargo.toml、Cargo.lock、src/business.rs。源 HEAD 分别为 1783c5c、b97ec36（文件取工作树当前字节，不假定等于 HEAD）；原始选定文件实验前后 hash 一致。规则文件是明确的合成规则，不代表实际宿主规则链。

以下为上一批 contextVersion=1 时的历史成本样本（不是当前 v3 性能承诺）：每个抽样库连续测 3 次、预算 8000 data bytes：

| 抽样 | context 毫秒样本 | 中位数 | 只 resolve 中位数 | data bytes | 正文 bytes / 截断 |
| --- | --- | --- | --- | --- | --- |
| Steward | 1829.78 / 1802.60 / 1733.47 | 1802.60 | 351.08 | 4405 | 2026 / 否 |
| Mailroom | 2117.91 / 1973.97 / 2105.89 | 2105.89 | 372.02 | 7999 | 5489 / 是 |

两个抽样库均通过：相同 HEAD 下文件变化、锁文件变化、合成规则变化、仅 HEAD 变化令指纹改变；重复不变读取指纹稳定；修改 Mailroom 抽样不改变 Steward 抽样指纹；跨项目 source ID 请求被拒绝。临时库/仓库在实验结束后释放，未创建真实项目登记。

这是小样本现场成本而非性能 SLA。resolve 不做文件双读/规则导航/Git 状态检查，不能作为功能等价的提速基线；data bytes 也不是 tokens，Mailroom 截断不能视为等信息量压缩。结论是当前入口仍有约 1.8–2.1 秒成本，尚未证明事实复用或 token 节省；真实全仓、宿主规则与环境失效、Pi 注入仍待验证。
