# 旧版 v7 归档迁移到当前数据库

这是显式离线迁移，不是默认打开数据库时的自动升级；不适用于 Markdown 任务、旧 schema 1 或当前试运行数据库合并。

## 范围与前置条件

- 源是旧构建的 `schema_migrations` 版本 1～7、`user_version=0` 数据库快照。使用 SQLite 在线备份取得一致快照，保留原库及备份；不要只复制运行中 WAL 数据库的主文件。
- 本轮仅支持所有 Task 已关闭、没有当前执行 Session 或 Worktree 绑定的归档。非空旧 `worktree_path_key`、歧义旧 Key、未知表/列或损坏数据拒绝迁移。
- 源和目标必须是绝对路径；目标主文件及 `-wal`、`-shm`、`-journal` sidecar 必须全部不存在（包括符号链接）。开始复制前和发布前均检查；发现残留文件直接拒绝，不自动删除。迁移期间不得有其他进程使用目标路径。禁止覆盖、合并或原地修改；重复运行应使用另一个新路径，不能清空既有目标来规避检查。
- 迁移期间不再向旧库写业务记录；命令读取的是源的一致快照，不会把后续旧库变化自动同步到目标。

## 命令

```bash
cargo build -p taskctl --bin taskctl --locked
# 以下路径是占位符，需要替换为本机备份和新正式数据库的绝对路径。
taskctl --database /absolute/new/steward.db --json --yes database import-v7 --source /absolute/backup/v7.db
```

迁移入口 `Service::import_legacy_v7`：

1. 显式确认后以 SQLite READ_ONLY + query_only 打开源，并固定读取事务。
2. 校验 Schema、表列、任务范围、quick_check 和 foreign_key_check。
3. 在目标同目录的私有临时目录初始化当前 schema 4，单事务复制 Task、Session、Checkpoint、Note、History、Import。
4. 保留所有 ID、Task version、时间戳、状态、继续关系、JSON 原文和 Import BLOB；保留 AUTOINCREMENT 高水位，避免复用已删除 ID。
5. 逐行逐字段比对所有复制内容，校验外键、数据库完整性及当前公开任务上下文/History 读取。
6. 关闭并刷盘临时数据库后，通过不覆盖既有路径的原子 hard link 发布新库。文件系统不支持 hard link 时明确失败，不降级成覆盖写。

失败不发布部分目标库；只清理本命令创建的临时目录。目标目录可能已创建，但已有文件不变。源库不会被修改。

旧 `schema_migrations` 是历史结构元数据，不导入；`tasks.worktree_path_key` 仅允许为 NULL 并省略。新版 `session_events` 初始化为空，因为旧库不存在 Hook 观测记录。Schema 4 的 `tasks.project_id` 留空，`projects/project_history/components/repositories/source_roots/task_components` 为空，不从旧任务文本推断项目；此命令不支持 Schema 2/3 活动库升级。

复制归档不属于 Task 业务更新：不伪造新的 History、Session 或 Task version，不重新打开任务。迁移核验以命令结果及外部报告记录，不写入旧业务 History。

## 验证与切换

- 用新版项目内 CLI 对目标运行 `doctor`、`task list --view recent`、`task context`、`history`、`task notes`。
- 比对源/目标所有业务表、序列高水位和关闭状态；备份及原库保持可回退。
- 若需试验后续创建/修改，在目标的副本上测试，避免污染正式归档。
- 迁移命令不安装二进制、不切换默认库、不修改 Pi 全局配置、不启动服务、不读取 Markdown Registry。
- 人工验证后另行决定正式服务/适配器切换；不要用旧版全局 CLI 打开新版数据库。

测试：`cargo test -p steward-application --test migration`；CLI 确认和目标保护测试见 `crates/cli/tests/migration_contract.rs`。
