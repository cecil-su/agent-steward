# 任务内需求与待确认事项

## 使用方式

一个 Task 可以包含多项需求。用户描述需求、查看进展并回答必要问题；Agent 负责拆分、去重、维护需求状态与结果，以及更新已答复的确认事项。需求不自动拆成独立 Task，不要求用户逐项维护状态。

需求当前态保存在同一 Steward 数据库，通过专用接口读取，不从 Note 或 Checkpoint 的文字推算。旧任务返回 `work: null` 表示尚未整理，不代表没有需求或已经完成。旧历史任务不自动批量转换。

### 需求状态

| 值 | 含义 |
| --- | --- |
| todo | 待处理 |
| in_progress | 进行中 |
| blocked | 受阻；nextStep 必须说明阻塞及恢复行动 |
| paused | 暂缓 |
| done | 已完成；必须保存对应结果和事实依据 |
| cancelled | 已取消 |

Agent 根据实际需求、相称的检查和最新事实维护进展。不能将计划当结果，也不对所有简单改动一律增加部署或业务测试要求。暂缓、取消、重开或范围变化须有用户决定或明确事实依据。新要求导致返工时保留既有交付结果和历史，不将原交付改写成从未完成。

Task 的七种业务状态仍由用户选择。需求全部完成、确认全部答复、测试通过或 Session 结束都不会自动修改 Task 状态，也不会领取、恢复或接管 Session。

### 待确认事项

仅提出需要用户业务选择、Agent 无法自行取得的关键资料或具体操作授权的问题。先核实现状，排除已解决、重复、过时和 Agent 可以自行查清的事项。每项包含关联需求、问题、推荐方案及影响。

状态为 `open`、`resolved`、`withdrawn`。关闭时保存答复或撤回理由及依据，不删除历史。一个问题待答复不自动阻断整个任务。Agent 收到用户自然语言答复后更新关联条目；推荐方案本身不是用户的决定，也不构成执行或远程写入授权。

## 数据与事务

当前数据库继续使用 **Schema8**，CLI/HTTP envelope3、UI合同5、包格式1不变。不增加表、不原地迁移或改写旧业务记录。

每次有效更新在既有 `history` 中增加 `task.work_updated` 事件，`payload` 包含：

- `work`：格式版本为1的完整类型化当前快照；
- `reason`：本次更新依据；
- `changedRequirementIds`、`changedConfirmationIds`：实际改变的编号。

读取按 Task 和事件类型定位 sequence 最大的快照，不扫描或解析 Note 正文。快照与 Task.version 增量、History 序号在同一写事务提交。失败全部回滚；同值更新仍校验版本但不递增版本或历史。冲突/结果未知后先重新读取并判断，不盲目重放。

需求字段：`id/title/acceptanceCriteria/status/result/nextStep/evidence/updatedAt`。

确认字段：`id/requirementIds/question/recommendation/impact/status/answer/evidence/updatedAt`。

更新采用固定编号的局部补丁；未提供的字段和未列出的条目保持不变。补丁不执行删除；单需求通过[专用删除入口](24-删除任务与需求.md)从当前快照移除，并处理确认引用、保留旧History和禁止已删除ID复用。每任务最多100项需求、100项确认；快照和输入各不超过256 KiB。编号为1—64个ASCII字母、数字、短横线或下划线；同类编号不能重复，确认只能关联同一 Task 的现有需求。

标题最多300字符；完成条件、结果、问题、建议、影响、答复及更新依据各最多4000字符；nextStep最多2000字符；每项最多20条非空依据，每条最多2000字符。依据是已核实事实的说明或引用，不自动验证文件、代码、发布或业务事实。不得保存凭据、消息全文或隐藏推理。

未知格式、损坏快照、无效引用、非法状态和未知输入字段明确报错，不返回伪造的空清单。当前实现不提供跨任务需求统计索引、依赖调度、独立需求版本或专门的History分页；任务历史保留每次完整工作快照。

## CLI 与 HTTP

```text
taskctl --database DB --json task work TASK
taskctl --database DB --json --input - task work-update TASK --if-version VERSION
taskctl --database DB --json task context TASK --require-read-only
```

`work-update` 从 stdin 或全局 `--input FILE` 读取：

```json
{
  "reason": "用户明确提出预览需求",
  "requirements": [
    {"id":"R1","title":"图片预览","acceptanceCriteria":"按确定的尺寸预览","status":"in_progress"}
  ],
  "confirmations": [
    {"id":"Q1","requirementIds":["R1"],"question":"使用300px还是原图？","recommendation":"300px","impact":"原图增加流量"}
  ]
}
```

后续答复补丁只更新相关字段：

```json
{
  "reason": "用户选择300px",
  "requirements": [{"id":"R1","nextStep":"实现300px预览"}],
  "confirmations": [{"id":"Q1","status":"resolved","answer":"用户选择300px","evidence":["本轮用户明确答复"]}]
}
```

- `GET /api/tasks/{id}/work` 返回 `task/work`。
- `GET /api/tasks/{id}/context` 在同一只读快照中提供 `work`，不受后续 Note 的50条截断影响。
- `POST /api/commands/task-work-update` 接收 `taskId/expectedVersion/input`。沿用管理员、Host/Origin、CSRF及合同检查；reader不能写入。
- CLI `task context` 文本输出和页面复制上下文包含需求及确认项当前态，历史内容仍可作为依据查询。

## 页面

原生与React详情读取同一context.work，展示需求状态、结果、未决问题和可展开的完成条件/依据及已处理问答。原生SSE重新读取当前快照；缺失、未知格式、未整理与空清单分别提示。除专用删除入口外，页面不增加需求编辑或状态写入口；用户可由Agent通过CLI/HTTP维护。React保持业务只读。

## 验证入口

cargo test -p steward-application --test task_work、cargo test -p taskctl --test task_work及server HTTP合同回归使用隔离合成数据；前端TaskWorkPanel和native-work回归验证展示、历史问答及空/不可用状态。不代表正式环境已升级。
