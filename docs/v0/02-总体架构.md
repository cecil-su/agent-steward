# 总体架构

## 1. 架构原则

初版使用 Rust 开发 CLI。M1–M3 初版 CLI 是唯一入口；M4/M5 增加 Hook 和本地 HTTP/GUI，共用业务规则。Task、Session、Checkpoint 和 Worktree 逻辑集中在 Application Service 中，所有入口复用这些规则。

```text
人类 / AI 窗口
       │
       ▼
  taskctl CLI（Rust）
       │
       ▼
Application Service
  ├─ Task Service ────────── SQLite Repository
  ├─ Session Service ─────── SQLite Repository
  └─ Worktree Service ────── Git Adapter ── Git / 文件系统

M4：通用 JSON Hook / Runtime Adapter ──► Application Service
M5：内嵌或外置同源 Web GUI ── Rust Local Daemon ──────► Application Service
```

SQLite 数据库只保存在服务所在本机，由 `taskctl`、`task-hook` 或 `taskd` 经同一 Application Service 打开，不需要独立数据库服务，也不支持多台机器共享同一数据库。Git HEAD、dirty、staged、untracked 和 Worktree 实际存在状态始终来自实时观察。

## 2. Rust Workspace

```text
Cargo.toml
crates/
├─ core/                 Task、Session、Checkpoint 类型和状态规则
├─ application/          Commands、Queries、事务编排
├─ storage-sqlite/       SQLite 初始化和事务
├─ git-adapter/          Git 和 Worktree 观察/操作
└─ cli/                  taskctl 参数解析和结果渲染

crates/cli/src/bin/task-hook.rs   通用 JSON 元数据适配器
crates/server/                    本地 HTTP Daemon（含 web/ 静态 GUI）
```

M4/M5 复用同步 Application；HTTP 将这些调用放到有界 blocking 线程池，Core 不引入异步运行时。初版数据库访问采用同步模型，使用 `rusqlite`；M1 至 M3 不因尚不存在的网络服务引入异步运行时或 ORM。

## 3. 分层约束

### Core

- 保存 Task、Session 和 Checkpoint 的结构化规则；
- 不访问终端、SQLite、Git 或文件系统；
- 不直接输出文本或退出进程；
- 不包含多 Agent 编排和复杂权限状态机。

### Application Service

- 通过 Repository 接口读取、校验和更新数据；
- `claim`、`resume`、`checkpoint` 等行为只能在这里实现；
- 一次数据库 mutation 的 Task、Session、Checkpoint 和 History 变更必须在同一事务中提交；
- Worktree 命令先读取真实 Git 状态，再决定是否执行；
- Worktree 身份使用 CanonicalPath 和规范化 Git common-dir；Git 一旦启动，无论退出状态如何都重新观察并按真实现场分类结果；
- 不在数据库写事务中执行 Git 或 AI 客户端长操作；
- Hook 和 GUI 复用同一服务；主动 Runtime 控制尚未纳入。

### Adapter

- SQLite Adapter 负责 schema 初始化、事务和错误映射；
- Git Adapter 使用参数数组调用系统 Git，不拼接 Shell；
- M4 客户端适配器只上报实际可观察的元数据；
- Adapter 不根据聊天、测试或工具输出自动改变 Task 结论。

### Client

- AI 通过 CLI 主动读取和更新 Task；
- 不直接修改 SQLite 数据库；
- Git 状态由 CLI 观察，不由 AI 手工填写；
- Hook 失败时仍可退回显式 CLI 流程。

## 4. 进程和连接模型

每次 CLI 调用执行以下流程：

1. 解析全局数据库路径；
2. 打开 SQLite 连接并启用外键、busy timeout 和 WAL；
3. 读取 `PRAGMA user_version`；仅空数据库执行单一 schema 初始化，已有当前 schema 的查询不申请写锁；
4. 执行一个 Query 或 Command；
5. 输出人类文本或稳定 JSON 后关闭连接。

查询可以并发。写命令通过 SQLite 事务串行化，并使用请求携带的 Task expected version 执行 compare-and-swap，防止基于旧快照的调用静默覆盖。expected version 必须来自事务外的调用方读取结果，不能在同一写事务内现读现用。CLI 不要求常驻进程；M5 的 taskd 常驻并以 SSE 发送数据库变更通知，不代替 SQLite 的状态权威。

## 5. 标准结果

```rust
struct CommandResult<T> {
    schema_version: u32,
    ok: bool,
    data: Option<T>,
    warnings: Vec<Warning>,
    error: Option<TaskError>,
}
```

CLI 将其渲染为人类输出或稳定 JSON。诊断文本写入 stderr，不得破坏 stdout 的 JSON 合同。所有 Task mutation 成功时返回完整 Task 和新 version；版本冲突、已证明未改变现场的 Git 失败，以及可能改变现场的 Git 部分完成分别使用稳定错误码与结构化 details。具体 envelope、空值、错误码和兼容规则见 CLI 文档。初版不返回 `operationId`，因此不承诺携带旧 version 的请求级幂等；调用方使用当前 version 发起同状态命令时可以得到不写 History、不递增 version 的 no-op success。
