# 任务信息维护（#44）

## 合同

复用 `task update`，不新增 revise。允许 open/in_progress/blocked/closed 的描述、项目归属和组件范围维护；不要求领取、解除阻塞或重开。关闭仍使用原 close 合同，结束当前 Session 并清空当前关联、保留历史。update 禁止 status、closureOutcome、closureReason、closedAt、Session、Checkpoint、Worktree 字段。

- CLI 的 update/project/components 都必须给 `--yes --reason <非空修改依据>`。确认表示调用方已取得用户针对该任务、该版本和该 patch 的明确授权，不是工具自行确认，不是批量授权。
- HTTP 沿用 admin/reader、Origin、CSRF 等边界；`task-update/task-project/task-components` 都要求 `confirmed:true` 和非空 `reason`。这不是新的身份认证体系；reason 不存 Token、密码或隐藏推理。
- 应用层也校验确认和依据，缺失/false/空白拒绝；全部使用刚读取的 Task version，不自动重试冲突。
- update 的 patch：`taskKey/title/goal/scope/acceptanceCriteria/nextStep/project/components`。未知字段、空 patch、无变化 update 拒绝。省略字段保持不变。
- `project` 是项目引用字符串（例如 `"##1"`、`"1"`、唯一项目名称）或 null；不会自动创建项目。
- `components` 是最终项目内的名称数组，[] 显式清空；非数组、非字符串元素、超过200项、重复名称和跨项目组件拒绝。没有项目时只能选空集合。
- 有旧组件且换项目或清项目时，必须同时提供 components，不能默默清空；名称在新项目解析。`task project` 不承担隐式清空，需联合修改时用 update。
- 描述已设置后不可清空；标题继续校验命名规则；taskKey 仍只能首次设置。closed 的 nextStep 必须为空，completed 的描述完整性不放宽。
- 一个写事务完成 CAS、全部字段/关联修改、一次 version 增量和一条 History；关联表或 History 写失败全部回滚。
- update/project/components 共用实现。后两者保留同值 no-op，但仍先验证授权、项目/组件和 CAS，不写 History。
- History 保留原事件类型，追加完整 TaskView `before/after`、排序 `changedFields`、`confirmed:true`、`reason` 及项目/组件 ID。维护事件 sessionId=null，不冒充执行会话；既有 History/Session/Checkpoint 不覆盖或回填。

## 隔离示例

编号和 VERSION 都从当前隔离库查询，不可直接用于正式任务。

```json
{
  "goal": "修正后的目标",
  "project": "示例项目",
  "components": ["backend", "frontend"]
}
```

```bash
taskctl --database /absolute/test.db --json task show '#1'
taskctl --database /absolute/test.db --json task update '#1' --if-version VERSION --input patch.json --yes --reason '用户确认纠正项目归属及组件范围'
```

HTTP：`POST /api/commands/task-update`

```json
{
  "taskId": 1,
  "expectedVersion": 3,
  "confirmed": true,
  "reason": "用户确认纠正项目归属及组件范围",
  "patch": {"project": "示例项目", "components": ["backend"], "goal": "修正后的目标"}
}
```

清归属且清组件使用 `{"project":null,"components":[]}`，不是先清组件再换项目的两个事务。

## 兼容与发布

本改动不修改 schema 和关闭约束。旧数据及旧 History 原样保留，JSON envelope 不变。CLI 新增必需参数、HTTP 新增必需字段、Rust 三个维护方法新增 confirmed/reason 参数，属于写调用合同收紧，旧调用不能静默补确认。

UI API 合同为 `2`：后端常量、活动 UI 请求头、外置包清单和打包脚本使用同一版本。旧合同 `1` 的包被拒绝，旧页面请求在业务处理前返回 `409 UI_API_INCOMPATIBLE`；合同 `2` UI 不能单独发布到合同 `1` 后端。包格式仍为 `1`，不自动迁移数据库或替换正式服务。

仓库内 CLI/API/测试已适配；外部调用者（包括已安装 Pi steward_task 扩展）、旧可写 Web UI、脚本需明确传递授权及依据后才能使用新写合同。只读 UI 无需增加写入口。不得由适配器无条件填写 confirmed=true。本文新合同优先于旧示例中缺少确认/依据的调用。

本地发布不等于授权批量修改正式任务。正式数据库迁移、远程写入与关闭 #44 均不包含在能力开发中。
